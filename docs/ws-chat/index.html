ws-chat

Чат для локальной сети: текст, голос, файлы напрямую между устройствами.

Что это такое

Чат, который живёт внутри одной локальной сети. Ничего не уходит наружу: ни сообщения, ни файлы, ни голос, ни единого запроса со страницы к чужому серверу.

Один человек запускает сервер на своей машине, остальные открывают его адрес в браузере. Сервер хранит переписку и раздаёт клиент; голос, звонки и прямая передача файлов идут между устройствами напрямую, минуя его.

Текст

Каналы и личные переписки, история переживает перезапуск, поиск, реакции, ответы, правка и удаление своих сообщений.

Голос

Групповые голосовые каналы и звонок один-на-один. Звук идёт P2P, сервер только сводит участников.

Файлы

Вложения до 25 МБ — через сервер, зашифрованными. Что угодно любого размера — напрямую между устройствами.

Устройства

Аккаунт открыт где угодно разом. Вход на новом устройстве по короткому коду, без набора пароля.

С чего начать

cd ws-chat
cp .env.example .env
npm install
npm run dev

Дальше открыть http://localhost:3000. Адреса, по которым сервер виден с других устройств, печатаются при старте — их и раздавать.

Сразу о границах

Голос и звонки с чужих устройств не заработают, пока сервер не поднят по HTTPS: браузеры выдают микрофон только в защищённом контексте и молча отказывают в остальных случаях. Это решается одной командой — см. раздел «Запуск».

Запуск и настройка

Сборки нет: TypeScript исполняется как есть через tsx, фронтенд — обычные ES-модули без бандлера.

Мастер-ключ

Без него не открыть ни вложения, ни историю. Он лежит в DATA_DIR/upload.key; если каталог данных не переживает деплой, задавай UPLOAD_KEY явно. Потеряешь — данные не восстановить: сервер скажет об этом в лог и откажется писать поверх, чтобы не затереть то, что ещё можно спасти правильным ключом.

HTTPS

Микрофон, камера и WebRTC-медиа доступны браузеру только в защищённом контексте — это HTTPS или localhost. По http://<ip-хоста>:3000 с чужого устройства микрофон блокируется молча, даже без запроса разрешения.

npm run cert
npm run cert -- chat.local   # добавить своё имя
npm run cert -- --force      # заменить существующий

Скрипт сам находит адреса хоста и вписывает их в subjectAltName — без этого браузер отвергнет сертификат, даже если принять предупреждение. Ключ пишется с правами 600 в DATA_DIR/tls/, сертификат живёт 825 дней: это предел, после которого macOS и iOS перестают доверять вовсе. Команда печатает готовые строки для .env.

Предупреждение браузера останется

Сертификат самоподписанный, поэтому на каждом устройстве один раз придётся нажать «Дополнительно» → «Перейти». Доверия к самоподписанному сертификату иначе не получить. Шифрование при этом настоящее — трафик в сети не читается, включая пароль при входе. Полностью «зелёный замок» даёт только сертификат от публичного УЦ, а для него нужны домен и внешний адрес.

Аккаунты и устройства

Два способа войти: гостем и с паролем. Разница в том, что остаётся после выхода.

Гость

Называет только ник. Личность переживает и перезагрузку страницы, и перезапуск сервера, а заканчивается двумя способами: по кнопке «Выйти» или сама собой, если гостем сутки не пользовались. Второе важно — вкладку закрывают гораздо чаще, чем жмут «Выйти», и без срока годности ник оставался бы занятым навсегда.

В обоих случаях гость стирается целиком: аккаунт, все его сессии, сообщения в каналах, обе стороны личной переписки, реакции и вложения. Заодно вычищаются снапшоты цитат — они специально переживают обычное удаление сообщения, и без этого текст стёртого гостя остался бы висеть в чужих ответах.

Сутки считаются от последнего использования, а не от входа. Открытая вкладка тоже считается активностью: уборка не трогает тех, кто сейчас в сети.

С паролем

Ник закрепляется навсегда, история переживает выход, а выход гасит только текущую сессию. Гостем такой ник занять уже нельзя.

Пароль меняется в настройках: нужен текущий, новый берёт свежую соль, и все остальные сессии гасятся — если старый пароль увели, открытое под ним в других местах доверия больше не заслуживает. Сессия, с которой меняли, остаётся, иначе меняющий выбьет сам себя.

Несколько устройств разом

Устройства не выбивают друг друга. В списке участников ник показывается один раз, «вышел» объявляется только когда отключилось последнее. Личные сообщения и отметки прочтения приходят на все.

Голос при этом одноустройственный: вход в голосовой канал с нового устройства выводит из него прежнее. Два микрофона одного человека дают эхо, а сигналинг, адресованный по нику, не смог бы выбрать между ними.

Звонок, наоборот, звонит на все устройства адресата разом. Кто первым взял трубку, тот и говорит; остальным приходит отбой с причиной answered-elsewhere. После приёма сигналинг идёт не по нику, а между двумя конкретными соединениями — иначе SDP мог бы уехать на устройство, которое трубку не брало.

Вход по коду

На новом устройстве есть «войти с другого устройства»: оно показывает шесть символов, а там, где ты уже вошёл, этот код вводится в настройках, в разделе «Устройства». Пароль на телефоне набирать не надо.

Код живёт две минуты, работает один раз и умирает вместе с сокетом, который его просил. В алфавите нет нуля, единицы, I, L и O — код читают с чужого экрана.

Что спрашивают при подтверждении

Код отдаёт не чужой аккаунт, а твой собственный — чужому устройству. Главная опасность тут не подбор, а «введи этот код, чтобы подтвердить» от постороннего, поэтому подтверждение требует явного согласия с прямым предупреждением. Гость подключать устройства не может: передавать ему нечего.

Список устройств

В настройках видно, где открыт аккаунт и когда им пользовались в последний раз. Любое отзывается по отдельности — отозванное сразу отключается, и по его токену больше не войти. Рядом «выйти со всех устройств», если проще погасить всё разом.

Наружу отдаётся только публичный идентификатор сессии; хэш токена клиент не видит. Отозвать чужую сессию, подобрав идентификатор, нельзя — проверка идёт в пределах своего ника.

Общение

Текстовый костяк в духе Discord: именованные каналы плюс отдельный раздел личных переписок.

Каналы и личные

  • Каналы создаются и удаляются из сайдбара. Удаление уносит историю канала, последний канал удалить нельзя, всего каналов не больше ста.
  • Личные не зависят от присутствия: список собеседников строится по переписке, а не по онлайну. Написать можно тому, кого сейчас нет в сети — сообщение дождётся его в истории.
  • История живёт на сервере и переживает перезапуск. Клиент подтягивает её при открытии разговора.

Непрочитанное

Разговор с новыми сообщениями белеет и получает кружок со счётчиком справа (после 99 показывает «99+»). Личные всплывают наверх по свежести последнего сообщения; порядок каналов остаётся неизменным, чтобы список не прыгал под курсором.

Отметки чтения живут на сервере, а не в памяти вкладки: счётчики переживают перезагрузку и синхронизируются между устройствами — прочитал на телефоне, на ноутбуке кружок погас сам. Прочитанным считается то, что ты действительно видел: разговор открыт и лента внизу. Отметка только растёт, поэтому два устройства, читающие вразнобой, не возвращают друг другу уже разобранное.

Впервые вошедшему старый хвост непрочитанным не считается — истории чтения у него ещё нет. А вот разговор, заведённый пока знакомый аккаунт был офлайн, отсчитывается с нуля: его действительно не читали.

Сообщения

  • Правка и удаление своих сообщений, инлайн, с пометкой «изм.».
  • Реакции — палитра из восьми эмодзи, чипы со счётчиком и подсветкой своих.
  • Ответы — цитата над сообщением: полоса цвета акцента, имя автора, первая строка оригинала и миниатюра, если отвечают на картинку. Клик по цитате прокручивает к оригиналу с подсветкой. Снапшот цитаты переживает удаление оригинала.
  • Упоминания — своё имя выделяется, сообщение помечается.
  • Индикатор набора по каналу и по личке.
  • Ссылки кликабельны. Узнаются только явные http и https: голый домен слишком легко спутать с текстом. Схема проверяется повторно, адрес собирается элементом со свойством href, без разметки. Хвостовая пунктуация и скобка вокруг ссылки в неё не попадают.

Уведомления

Включаются в настройках, отдельной кнопкой: разрешение браузер выдаёт только в ответ на нажатие, а не при загрузке страницы. Приходят, когда окно свёрнуто, и только на личное сообщение или упоминание — всё подряд из каналов приучает нажимать «выключить». Подряд идущие сообщения из одного места схлопываются в одно окошко.

Работают только в защищённом контексте: по https или на самом localhost. С телефона по открытому адресу браузер их не даст, и кнопка в настройках честно скажет об этом вместо того, чтобы молча не работать.

Ключи устройств

Подготовка к сквозному шифрованию личных переписок. При входе устройство заводит себе пару ключей: закрытый остаётся в браузере помеченным как неизвлекаемый — его нельзя прочитать даже своим же кодом, можно только попросить браузер посчитать общий секрет, — а открытый уходит на сервер и живёт ровно столько, сколько живёт сессия. Вышел с устройства — писать в него больше нечем.

В шапке личной переписки стоит отпечаток собеседника — там, где с ним и разговаривают. Наведи, чтобы увидеть все его устройства целиком; нажми, чтобы получить тот же список строкой в ленте. Если у человека нет устройств с ключами, там будет сказано и это. В канале отпечатков нет: переписка там общая, и сквозного шифрования для неё мы пока не умеем.

Свой отпечаток лежит в настройках, в разделе «Устройства». Чужие смотрят правым кликом по нику → «Ключи устройств»; своё устройство там помечено отдельно. Отпечатки для того и нужны, чтобы сверить их с собеседником по другому каналу: без сверки шифрование защищает от подслушивания в сети, но не от подменённого сервера.

Пока ключи только заводятся и раздаются — сообщения по-прежнему шифруются на диске ключом сервера. Шифрование переписок ими — следующий шаг.

Контекстное меню

Правая кнопка собирает действия по тому, на чём щёлкнули: у сообщения — ответ, реакция, копирование текста, переход к оригиналу и, для своих, правка с удалением; у ника — личная переписка, упоминание и копирование; у канала — открыть, скопировать имя и удалить, а у голосового ещё и войти или выйти; у вложения — открыть картинку в просмотрщике, скачать и скопировать имя файла; у ссылки — открыть и скопировать адрес; на пустом месте ленты — отметить разговор прочитанным, открыть поиск и уйти в конец. Внутри поля ввода остаётся родное меню браузера: там правка, вставка и проверка орфографии, которых у нас нет.

Пункты копирования исчезают там, где буфер обмена недоступен. Он работает только в защищённом контексте, а с телефона чат чаще всего открывают по обычному http: пункт, который молча не сработает, хуже отсутствующего.

Поиск

Поле поиска стоит в шапке на виду; на узком экране места нет, и то же самое поле переезжает в саму панель результатов. Ищет по каналам и твоим личным перепискам. Доступ проверяется на сервере, а не в интерфейсе — чужие личные не найдутся, как точно ни угадай слово. Клик по находке открывает разговор и подсвечивает сообщение; если оно старше подгруженного куска истории, страница так и скажет.

Вложения

Файлы и картинки, до 25 МБ и до десяти штук на сообщение. Картинки показываются в ленте, прочее — карточкой-ссылкой. Файл можно вставить из буфера или перетащить в окно: скриншот не надо сначала сохранять на диск.

Клик по картинке открывает просмотрщик поверх чата: стрелками или клавишами ← и → листаются все картинки разговора — вся история, что хранит сервер, Esc закрывает. Ctrl или ⌘ с кликом по-прежнему открывает файл в новой вкладке.

Мелочи, которые заметны в работе

  • Лента не выдёргивается из-под курсора: автоскролл только когда ты и так внизу, иначе появляется плашка «новых: N».
  • Подряд идущие сообщения одного человека собираются в группу: имя пишется один раз, строки стоят вплотную. Пауза дольше пяти минут, чужая реплика посередине, новый день или ответ с цитатой группу обрывают.
  • Цвет кружка с буквой и подписи автора выводится из ника, поэтому у человека он одинаков на всех устройствах и не зависит от того, кто раньше вошёл.
  • При наведении на сообщение показываются ответ и реакция; правка, удаление и всё остальное живут в контекстном меню.
  • Панели участников, поиска и передачи файлов делят одно место справа: открытая вытесняет соседнюю.
  • День отбивается плашкой с датой: «Сегодня», «Вчера», дальше числом, а прошлогоднее — с годом. Плашка держится у верхнего края, пока листаешь этот день, и с наступлением полуночи перестаёт врать в открытой вкладке.
  • Обрыв связи не глотает сообщения — отправленное копится в очереди, видно в шапке, и уходит после переподключения. Сообщение, ушедшее в уже мёртвый сокет, повторяется после восстановления связи: оно несёт метку отправки, и сервер узнаёт по ней повтор, поэтому второй копии не появится.
  • Непрочитанное попадает в заголовок вкладки: свёрнутое окно иначе ничего не скажет.
  • На узких экранах сайдбар уезжает за край и открывается гамбургером.

Голос и звонки

Звук идёт между устройствами напрямую. Сервер видит только сигналинг — кто с кем соединяется, но не что говорят.

Голосовые каналы

По умолчанию general и games, новые создаются из сайдбара. Клик подключает, под каждым каналом видно, кто в нём. Ты в одном канале за раз, клик по другому переключает.

  • Аудио — WebRTC-mesh внутри канала: каждый шлёт микрофон каждому, Opus поверх UDP и SRTP. Сигнал ходит только между участниками одного канала.
  • Нижняя панель: микрофон, заглушка (глушит звук всех и свой микрофон заодно) и выход.
  • iceServers пуст — на локальной сети хватает host-кандидатов, трафик не покидает сеть.

Мут виден остальным

У молчащего в списке канала гаснет зелёная точка и появляется перечёркнутый микрофон. Без этого собеседники ждали бы ответа от того, кто их не слышит.

Наружу уходит не сам мут, а то, слышно тебя или нет: заглушка выключает микрофон тоже, и снаружи это неотличимо. Состояние держит сервер, поэтому вошедший позже сразу видит, кто уже молчит. Мут принадлежит устройству, а не аккаунту — выход из канала и переход на другое устройство начинают с живого микрофона.

Удаление голосового канала выгоняет тех, кто в нём сидел: клиент гасит микрофон и сворачивает соединение. Иначе сервер про них уже забыл, а у них горит микрофон и панель показывает канал, которого нет.

Звонок один-на-один

В личке есть кнопка «Позвонить»: приглашение, входящий баннер с «Принять / Отклонить», соединение. Звонящий шлёт offer после приёма, поэтому glare не возникает. Если ника нет в сети — придёт отбой с причиной offline; если абонент уже в звонке — автоматический отказ с busy.

Панель звонка живёт поверх любого канала и показывает, кто говорит (зелёное кольцо, детект речи через WebAudio локально), уровень по каждому участнику и качество связи из getStats() раз в секунду: задержку, потери, джиттер, битрейт, кодек и используемый транспорт. Точка слева меняет цвет по качеству. Панель перетаскивается за верхний хват.

Настройки звука

Шестерёнка снизу слева: выбор микрофона и динамика, шумоподавление, эхоподавление, автоусиление. Смена устройства применяется на лету в активном голосе или звонке. Там же выбор шрифта — все три забандлены локально и работают офлайн.

Границы

Mesh рассчитан на небольшую группу: каждый шлёт каждому, и на десятках участников это перестанет работать — нужен SFU. Демонстрации экрана и громкости на участника пока нет.

Передача файлов напрямую

Отдельный путь для файлов, которые не должны попадать на сервер вообще: они идут между устройствами по WebRTC DataChannel.

Кнопка со скрепкой в шапке открывает панель поверх чата — это встроенный lan-drop. Лимита в 25 МБ, как у вложений, здесь нет, и на диск сервера ничего не ложится.

Как это устроено

  • Сигналинг живёт на отдельном пути /drop того же порта и требует сессию: клиент первым сообщением предъявляет токен, и только тогда попадает в реестр. Без этого сигналинг был бы дырой в обход всего входа — кто угодно в сети видел бы список устройств и стучался к ним.
  • Пир называется ник · устройство, поэтому два окна одного человека различимы. Адресуются именно устройства, а не ники: файл идёт в конкретное.
  • Приём подтверждается вручную. Входящее пишется на диск по мере поступления, так что размер файла не упирается в память вкладки.

Соединение живёт, пока ты в чате

Соединение с сигналингом держится всё время, пока ты в чате, а не только пока открыта панель. Иначе прислать файл можно было бы лишь в те минуты, когда получатель смотрит именно в неё. Предложение, пришедшее при закрытой панели, метит кнопку в шапке и попадает в счётчик заголовка вкладки.

Отмена

Начатую передачу можно прервать с любой стороны. Отмена идёт по сигналингу, а не по каналу данных: канал бывает забит очередью чанков или уже мёртв, а отмена должна дойти сразу. Отмена до ответа снимает предложение у получателя; недописанный файл не закрывается, а отбрасывается.

Где запасной путь

Запись на диск по мере поступления работает через File System Access API. Там, где его нет — Firefox, Safari, — включается сборка в памяти вкладки с сохранением в конце. Об этом предупреждают до согласия на приём, а не после.

Безопасность

Что лежит на диске, чем закрыто и от чего это на самом деле защищает.

Что лежит на диске

ФайлСодержимоеКак защищено
store.jsonпереписка, каналы, реакции, отметки чтенияAES-256-GCM на ключе, производном от мастер-ключа
uploads/*вложенияAES-256-GCM; имя файла — HMAC от содержимого
accounts.jsonники, scrypt-хэши паролейправа 600; пароль не восстановить и без шифрования
sessions.jsonники, sha256 токеновправа 600; по хэшу токена войти нельзя
upload.keyмастер-ключправа 600

История и вложения шифруются разными ключами: у истории он выводится из мастер-ключа через HMAC. Утечка одного не раскрывает второе, но хранить и переносить надо по-прежнему только один.

Аккаунты и сессии намеренно не шифруются. Там нет ничего, что шифрование защитило бы дополнительно: пароли уже посолены и прогнаны через scrypt, а от токенов хранятся только хэши.

Вход

  • Пароль — scrypt (N=2¹⁵, r=8) с индивидуальной солью, сверка через timingSafeEqual. Проверка стоит около 100 мс: вход этого не замечает, перебор дорожает на порядки.
  • Вход под несуществующим ником всё равно прогоняет KDF по пустышке, чтобы по времени ответа нельзя было понять, какие ники заведены. Ответ на неверный ник и на неверный пароль одинаковый.
  • Серия промахов замедляет вход по этому нику с нарастанием до пятнадцати минут.
  • Сессия — случайный токен; на сервере лежит только его sha256. Утёкший файл сессий не даёт войти ни за кого.
  • Сессия живёт 30 дней у аккаунта с паролем и сутки у гостя. На аккаунт хранится не больше десяти — самые старые вытесняются.

Вложения

Файлы не лежат в открытом виде и не раздаются по угадываемой ссылке. Токен нужен и для загрузки, и для скачивания, и передаётся заголовком, а не в URL: открыть /uploads/<id> в браузере не выйдет, вернётся 401.

Байты сжимаются gzip, если это что-то даёт, и шифруются AES-256-GCM. Метаданные открыты, но входят в AAD — подменить их, не сломав проверку, нельзя. Имя блоба — HMAC(ключ, sha256(содержимое)): одинаковые файлы занимают одно место, но по имени нельзя понять, что внутри, как выдавал бы обычный хэш.

Скачать вложение может только участник разговора, в котором оно приложено: картинку из чужой личной переписки не вытащить, даже зная id. Размер и mime берутся из самого блоба, а не из слов клиента. В ленте показываются только заведомо безопасные растровые форматы, всё остальное отдаётся как вложение с nosniff, чтобы svg и html не исполнились в origin.

Соединения

Сокет стоит памяти ещё до того, как назовётся, поэтому их число ограничено и по каждому адресу, и в сумме (CONNS_PER_SOURCE, CONNS_TOTAL). Отказ выносится до рукопожатия.

Сокет, который открыли и не представились, закрывается через AUTH_GRACE_MS. Хартбит его не заметил бы: на пинги такое соединение отвечает исправно. Устройство, ждущее подтверждения кода привязки, ждёт законно — выдача кода продлевает срок до времени жизни самого кода.

WebSocket не подчиняется правилу общего источника, поэтому при апгрейде сверяется Origin: иначе любая открытая страница могла бы соединиться с чатом браузером своего читателя. Пустой Origin пропускается — это не браузер, а свой клиент или приложение.

Недоверенный ввод

Всё, что приходит по сокету, разбирается на границе: длины, типы, белые списки. Имена каналов проверяются по шаблону, а не по чёрному списку, поэтому ../ и разделители пути туда не проходят. Размер кадра ограничен ещё до разбора. На разбор входящих есть отдельный набор тестов.

От чего это не защищает

Сервер видит всё: он хранит переписку и может её прочитать. Шифрование на диске спасает от украденного диска и от чужого доступа к файлам, но не от того, кто владеет сервером.

Сквозного шифрования нет. И пока клиент приходит с того же сервера, оно не решит задачу целиком: сервер может подменить сам скрипт. Выход — упакованное приложение, которое приносит свой код.

По http:// пароль виден любому, кто слушает сеть. На экране входа об этом висит предупреждение; гостевого входа это не касается. Решение — HTTPS. Вариант с SRP, при котором пароль вообще не покидает устройство, пока в планах.

Развёртывание на своём сервере

Два пути: одной командой через Docker или в кластере Kubernetes. Первого хватает почти всегда.

Что нужно знать заранее

Чат держит разговоры, присутствие и голосовой сигналинг в памяти своего процесса. Поэтому копия у него ровно одна, и «добавить ещё подов» не сделает его быстрее — сделает два независимых чата, где люди не видят друг друга. Масштабировать здесь нечего, и это свойство замысла, а не недоделка.

Второе: ключ шифрования и том с данными должны жить вместе. Потеряешь ключ — переписку и вложения не открыть уже никак.

Docker: самый короткий путь

Нужен сервер с установленным Docker. Всё остальное — три команды.

git clone https://github.com/h4root/webtools
cd webtools

# ключ шифрования: сгенерируй один раз и сохрани у себя
echo "UPLOAD_KEY=$(openssl rand -hex 32)" > .env

docker compose up -d

Чат поднимется на порту 3000. Проверить, что он жив: curl localhost:3000/health — ответ {"status":"ok"}.

Данные лежат в томе data и переживают перезапуск и обновление образа. Обновиться: docker compose pull && docker compose up -d. Остановить: docker compose down — том при этом остаётся.

Порт 3000 наружу открывать не надо

По http:// браузер не даст микрофон никому, кроме как на самом сервере, а пароль при входе будет видно в сети. Поставь перед чатом любой обратный прокси с сертификатом — Caddy, nginx, Traefik — и отдавай наружу уже https. Прокси должен пропускать заголовки апгрейда WebSocket и не рвать долгие соединения.

Kubernetes

Готовые манифесты лежат в deploy/k8s. Порядок такой:

# 1. пространство имён
kubectl apply -f deploy/k8s/namespace.yaml

# 2. ключ шифрования — командой, не файлом
kubectl -n ws-chat create secret generic ws-chat-key \
  --from-literal=UPLOAD_KEY=$(openssl rand -hex 32)

# 3. поправь домен в deploy/k8s/ingress.yaml, затем
kubectl apply -k deploy/k8s

Проверить: kubectl -n ws-chat get pods и kubectl -n ws-chat logs deploy/ws-chat.

Почему манифесты выглядят именно так

  • Одна копия и стратегия Recreate. Обновление сначала гасит старый под и только потом поднимает новый: два пода подрались бы за том и развели два разных чата.
  • Готовность спрашивает /health, живость — только порт. Готовность отвечает «нет», если сервер не может сохранять историю, и под убирают из балансировки. Вешать на это живость нельзя: неверный ключ перезапуском не лечится, вышел бы вечный цикл перезапусков.
  • TRUST_PROXY=1. Внутри кластера адрес клиента приходит от ingress-контроллера. Вне кластера этот флаг включать нельзя: заголовок подставляет кто угодно, и ограничение попыток входа обходится случайным адресом.
  • Таймауты в ingress подняты до часа. Значения по умолчанию рвут долгие соединения чата молча.
  • Контейнер не root, файловая система только на чтение, кроме тома с данными и /tmp.

Сколько это ест

Запрошено 50 мКПУ и 96 МБ, потолок — одно ядро и 256 МБ. Для десятка человек в одной сети этого с запасом: тяжёлое здесь — голос и передача файлов, а они идут между устройствами напрямую и через сервер не проходят.

Резервная копия

Достаточно скопировать каталог данных целиком: в нём и история, и аккаунты, и вложения, и ключ.

# docker
docker run --rm -v webtools_data:/data -v "$PWD":/backup alpine \
  tar czf /backup/ws-chat-backup.tar.gz -C /data .

# kubernetes
kubectl -n ws-chat exec deploy/ws-chat -- tar cz -C /data . > ws-chat-backup.tar.gz

Восстановление — распаковать обратно в тот же том до запуска.

Как принято резать

Модуль — это фабрика с явными зависимостями: createVoice, createSearch, createGate. Состояние держится приватным внутри, наружу торчат только нужные функции. Новая заметная функциональность заводится сразу своим модулем, а не дописывается в существующий «пока что»: app.js дважды доходил до полутора тысяч строк, и оба раза разбор превращался в отдельную работу.

Тесты

npm test
npm run typecheck
npx vitest run src/store.test.ts
npx vitest run -t "поиск"

Логика на сервере покрывается по полному циклу: сначала падающий тест, потом реализация. На клиенте так проверяется не всё: разбор ссылок, ключи разговоров и таймеры индикатора набора вынесены в модули и покрыты тестами. DOM, WebRTC и всё, что требует человека или устройства, проверяется руками.

Здоровье и кэш

GET /health отвечает без входа и не кешируется. Он смотрит не на то, что процесс поднят, а на то, способен ли сервер сохранять: если история не пишется — не тот ключ, нет прав на файл, — ответ будет 503 и degraded. Про то, кто в чате, наружу не уходит ничего.

Шрифты и вендор отдаются с недельным сроком кэша, код приложения — с no-cache. Хеша в имени файла нет, поэтому вечный срок был бы ловушкой: обновление не доехало бы до тех, кто уже открывал страницу.

Протокол

JSON поверх WebSocket. Клиент отправляет auth, message, history, search, read, edit, delete, react, typing, управление каналами, а также voice-* и call-* для сигналинга.

welcome несёт номер версии протокола. Клиент сверяет его с тем, с которым собран, и, если сервер обновился под открытой вкладкой, показывает просьбу перезагрузиться вместо того, чтобы молча не понимать новых сообщений.

Сервер отвечает welcome, channels, dms, presence, message, history, reads, edited, deleted, reaction, typing, system, error и зеркальными сигнальными сообщениями. Вложения ходят вне сокета: POST /upload и GET /uploads/:id с токеном в заголовке.

Стороннее
