lan-drop

Передача файлов между устройствами в одной сети, напрямую из браузера.

Что это такое

Открываешь одну страницу на двух устройствах в одной сети — они видят друг друга, и файл идёт с одного на другое напрямую.

Сервер здесь сводит устройства и пересылает служебные сообщения, по которым они договариваются о соединении. Сами байты файла через него не проходят и на его диск не ложатся, поэтому нет ни предела размера, ни следа на сервере.

Любой размер

Ограничения на объём нет: файл идёт мимо сервера и пишется на диск по мере поступления, не накапливаясь в памяти вкладки.

Приём с согласия

Получатель видит отправителя, список файлов и общий размер. Соединение создаётся только после его согласия.

Не выходит из сети

Внешние STUN-серверы не используются: внутри одной сети устройства находят друг друга сами.

Встраивается

И серверная часть, и виджет подключаются к чужому приложению. Так он и живёт внутри ws-chat.

Родство

Подход тот же, что у Snapdrop и PairDrop: устройства получают автоимя и договариваются о прямом соединении через сервер. Инстанс рассчитан на одну сеть, поэтому все подключённые видят друг друга — без деления на комнаты по подсети, которое ломается на IPv6.

Запуск

Сборки нет: TypeScript исполняется как есть, фронтенд — обычные модули без бандлера.

cd lan-drop
cp .env.example .env
npm install
npm run dev     # http://localhost:3000

Дальше открыть http://<ip-хоста>:3000 на двух устройствах в одной сети. Они появятся друг у друга плитками — нажать на плитку, чтобы отправить файлы.

Куда сохраняется принятое

В браузерах, умеющих писать на диск по ходу приёма, спрашивается место: для одного файла — куда сохранить, для нескольких — папка. Там, где этого нет (Firefox, Safari), файл собирается в памяти вкладки и сохраняется в конце, и об этом предупреждают до согласия на приём, а не после.

Как устроено

Сервер знает, кто сейчас в сети, и передаёт между ними непрозрачные для себя сообщения. Всё остальное решают сами устройства.

устройство A ──ask: список файлов──▶ сервер ──▶ устройство B
устройство A ◀──accept / decline───── сервер ◀── устройство B
устройство A ──offer / ice─────────▶ сервер ──▶ устройство B
устройство A ◀──answer / ice──────── сервер ◀── устройство B
устройство A ◀═══ прямой канал: файлы ═══▶ устройство B
  • Служебное сообщение уходит конкретному адресату по его идентификатору, а не всем подряд. Для сервера его содержимое непрозрачно, поэтому согласие на приём живёт целиком в клиентах.
  • Устройство называется по автоимени, так что два окна одного человека различимы. Адресуются именно устройства: файл идёт в конкретное.
  • Кратковременный обрыв не рвёт передачу — на восстановление даётся восемь секунд.
  • Внешние STUN не нужны: внутри сети хватает прямых адресов, и трафик её не покидает.

Отмена

Прервать можно с любой стороны. Отмена идёт по служебному каналу, а не по каналу данных: тот бывает забит очередью кусков или уже мёртв, а отмена должна дойти сразу.

Отмена до ответа снимает предложение у получателя. Отправитель проверяет её между кусками и не досылает остаток в закрытый канал. Приёмник после отмены молчит: поздний кусок отбрасывается, следующий файл не открывается, а недописанный не закрывается, а сбрасывается.

Встраивание в своё приложение

Пакет отдаёт два входа: серверную часть и виджет. Ни один не привязан к конкретному серверу или странице.

Серверная часть

Сигналинг вешается на отдельный путь рядом с другим приложением на том же порту:

import { WebSocketServer } from 'ws';
import { attachSignaling } from 'lan-drop';

const dropWss = new WebSocketServer({ noServer: true });
attachSignaling(dropWss, {
  authenticate: (raw) => {
    const session = mySessions.resolve(JSON.parse(raw).token);
    return session ? { name: session.user } : null;
  },
});
Про authenticate

Без этого хука сигналинг открыт всем, кто дотянулся до пути. Для отдельного инстанса в доверенной сети это нормально, для приложения со входом — нет: кто угодно увидел бы список устройств и стучался к ним в обход всей авторизации.

С хуком устройство молчит, пока первым сообщением не предъявит пропуск: до этого оно не попадает в реестр, никого не видит и ничего не шлёт. Что считать пропуском, решает хозяйское приложение — lan-drop про его сессии не знает ничего. Непредставившихся отключает по таймауту.

Виджет

import { mountLanDrop } from 'lan-drop/client';

const drop = mountLanDrop(document.getElementById('drop'), {
  url: `ws://${location.host}/drop`,
  auth: () => ({ token: mySessionToken }),
});
// drop.destroy() — снять виджет и закрыть соединения

auth — функция, а не готовое значение, и это важно: она вызывается при каждом подключении, включая переподключение после обрыва, а токен к тому моменту может смениться.

Живой пример

Именно так lan-drop работает внутри ws-chat: сигналинг живёт на пути /drop того же порта и требует сессию чата, а виджет открывается панелью поверх переписки.

Разработка

Раскладка

src/
  protocol.ts     типы и проверка входящих сообщений
  names.ts        автоимена устройств
  signaling.ts    реестр пиров и пересылка — чистая логика
  attach.ts       подключение сигналинга к любому WebSocketServer
  index.ts        публичный вход пакета
  server.ts       отдельный сервер: статика и сигналинг

public/
  transfer.js     сборка входящих файлов, без DOM и WebRTC
  lan-drop.js     виджет и WebRTC
  app.js          отдельная страница
  index.html styles.css

Где проходит граница тестируемого

Приём файлов вынесен в transfer.js: он знает про управляющие сообщения, границы файлов и учёт байтов, но не про DOM, WebRTC и способ сохранения — пишет в подставляемый приёмник. Поэтому он покрыт тестами, хотя лежит в public/.

npm test
npm run typecheck

Тестами покрыты сигналинг, разбор протокола, точка встраивания и сборка входящих файлов.

Что проверяется только руками

WebRTC, выбор места сохранения и разметка без браузера не запускаются. Это проверяется в двух окнах: отправка нескольких файлов, отказ от приёма, обрыв на середине.
